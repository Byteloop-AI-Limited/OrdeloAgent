Telegram starter kit: how the files fit together

A throwaway aiogram 3 + FastAPI bot. This page explains who calls whom, what each file owns, and how an invite link turns into a linked Telegram identity. Everything lives in tgram_starter/; delete the folder to remove it.

1. The big picture

Telegram never connects to your laptop directly. Either Telegram pushes each update to a public HTTPS URL (webhook), or your code pulls updates from Telegram (polling). The notebook is a third door: it calls the Bot API directly to send things.

Replies travel the other way: a handler calls message.answer(...) or bot.send_message(...), which makes an HTTPS call to Telegram, which delivers it to the user's app.

3. Life of one update

  1. A user taps a button or sends text. Telegram wraps it in an Update with an update_id and one payload (message, callback_query, edited_message, …).
  2. Webhook mode: Telegram POSTs the JSON to /telegram/webhook with header X-Telegram-Bot-Api-Secret-Token. app.py compares it to your secret and returns 403 on mismatch. Polling mode: aiogram fetches the same Update via getUpdates.
  3. The Dispatcher offers the update to routers in registration order: onboarding → interactive → basic. The first handler whose filter matches wins (CommandStart(), F.contact, DemoOrder.filter(), F.location, F.text, …). That is why the catch-all echo lives in the last router.
  4. The handler runs. settings is injected because bot_factory stored it with dp["settings"].
  5. The handler replies with an awaited Bot API call. For a callback it must also call query.answer() so the button stops spinning.
  6. The webhook route returns {"ok": true}. If it returns an error, Telegram retries.

4. Invite flow: from phone number to Telegram ids

A bot cannot find a Telegram id from a phone number and cannot message anyone who hasn't pressed Start. The invite link is the bridge.

identitytelegram_user_id
The person (from_user.id). Authorise actions on this.
destinationtelegram_chat_id
Where the bot sends (chat.id). Equal to the user id in a private chat, but stored separately.
display onlytelegram_username
Can change or be empty. Never an identity.
rulesClaim checks
Unknown, expired, revoked, or used by another account are refused. Same person pressing Start twice is fine.

5. Three ways to run it

APolling
uv run --project tgram_starter \
python -m tgram_starter.polling
No tunnel. Easiest for learning. Removes any webhook.
BWebhook
uv run --project tgram_starter \
uvicorn tgram_starter.app:app --port 3200
uv run --project tgram_starter \
python -m tgram_starter.webhook_cli set
How production works. Needs a public HTTPS URL.
CNotebook
# %% cells in notebook.py
Call the Bot API by hand. Cell 14 can run polling inside the kernel so the kernel's invites dict is the live one.
Webhook and polling are mutually exclusive. If get_updates returns a 409 conflict, a webhook is still set. Check with webhook_cli info.

6. Gotchas that explain the design

  • Router order matters. Specific handlers first, generic text echo last (bot_factory.py).
  • Always answer callbacks, including rejected or stale ones. Answering only clears the spinner; it is not the business confirmation.
  • Callback data ≤ 64 bytes. Typed classes like DemoOrder pack to ord:1042:a.
  • Escape user text before putting it in HTML messages.
  • The dict is per process. A restart forgets invites; two worker processes would not share them. Use one worker, and a real table later.
  • The webhook handler works inline. Fine here; the real service needs update-id dedupe and a durable queue (see ADR 0011).
