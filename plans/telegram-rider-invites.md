# Per-rider Telegram invites

**Status:** Plan for implementation and local verification. A database schema migration is required. No implementation or live test is recorded here.

## Rider and operator workflow

- Keep `https://t.me/ByteloopRidersBot?start=join` for verified contact onboarding. Add a personal link that skips phone sharing. Telegram's bulk `botinvite` feature is out of scope.
- Add `scripts/create_rider_invite.py`. The operator supplies one phone number in international format. The script normalizes it with the rider phone rules, calls a privileged database function, and prints only `https://t.me/ByteloopRidersBot?start=<code>` to stdout. Report invalid input or database failure on stderr with a nonzero exit code. Distribution is manual.
- For a missing phone, create one `rider_master` row with name, town, and vehicle set to `TBD` and status `inactive`. Issue for existing riders too, including riders with a Telegram link. Return the same pending link on rerun. Links have no expiry and can be claimed once. Running the script after a claim or revocation issues a new link.
- The bot links the rider as soon as it receives `/start <code>` in a private chat. Telegram itself may show **Start**. Ordelo adds no confirmation screen. Fill a `TBD` name from the Telegram first name when available. Resume the existing town and vehicle prompts for missing values. Activate an incomplete rider when both valid choices have been saved. For a complete existing profile, keep its profile, status, shift and pauses.
- A valid claim can replace the rider's previous Telegram link. If the claiming Telegram account is already linked to a different rider, refuse the claim and keep the invite pending. Unknown, revoked or used codes take the normal `start=join` path. A rider who just claimed a link can resume their profile through the normal linked-rider response. A temporary database error should tell the rider to retry.
- Send an ops alert for each successful claim, including a same-account claim or a move. Include a masked rider phone and new Telegram handle or ID. For a move, include the previous handle or ID. Never include the invite code or URL in alerts, logs, release notes, or screenshots. A forwarded pending link can link the recipient and give them access to rider jobs. Ops can revoke a pending link for that phone and reissue it. After a mistaken claim, revoke any outstanding link, reconcile the rider's jobs, and restore the intended link through the authorized operator workflow.

## Implementation

1. **Add the migration and update the canonical SQL.** Compare the target schema and grants with [`t_invites.sql`](../ordelo_datamodels/telegram/t_invites.sql) and [`t_rider_onboarding.sql`](../ordelo_datamodels/telegram/t_rider_onboarding.sql). Keep `rider_master` authoritative for identity. Store invitations in `public.t_invites` as `bot_key = 'rider'`, `rest_ref IS NULL`, and `expires_at IS NULL`. Add constraints that preserve the restaurant requirement and existing expiry default for `rest_admin`. Add a partial unique index on rider `phone_number` for pending invites and keep the existing admin uniqueness rule. Use an opaque, high-entropy URL-safe code with a distinct `ri_` prefix within Telegram's 64-character limit. Keep table and RPC access restricted to the service role. Existing rider and admin records need no historical backfill. [Telegram deep linking](https://core.telegram.org/bots/features#deep-linking)
2. **Add rider-specific issue, claim and revocation operations.** Issue under a per-rider lock with a uniqueness backstop, so concurrent reruns return the same pending code. Claim the pending invite and update `rider_master` in one transaction. Use `from_user.id` as `tuid` and the private `chat.id` as `tcid`. Lock consistently across issue, contact linking and invite operations. Use the existing unique `tuid` index to resolve races with other rider links. A failed claim leaves the rider and invite unchanged. Record claim time and actor on the invite for audit. Key claim retries and alert work by the committed claim, using the existing Telegram inbox where appropriate. A repeat delivery of the same Telegram update must resume that work without linking or enqueueing the alert again. An alert outage must leave retryable work and an observable failure. Record ambiguous Telegram sends without assuming they reached ops.
3. **Add the rider bot entry point and activation.** Wire the invite branch ahead of the existing linked-rider lookup in [`channels/telegram/rider/router.py`](../channels/telegram/rider/router.py). Route well-formed rider payloads through the protected Telegram update path and reuse the existing rider prompts, allowed choices and callback actor checks. Tie invite onboarding to the current claim and Telegram identity, so stale callbacks from the previous account cannot complete it. Save the final missing profile field and activate in one transaction. Leave ordinary contact onboarding on its existing activation path.
4. **Keep the phone proof and dashboard rules.** The invite grants the Telegram rider link. It provides no proof of phone ownership. Keep `phone_verified` false for a new invite-only actor and clear the old actor's phone proof on a move. Preserve valid proof on a same-actor claim. Inspect and test the existing revocation trigger and the dashboard's checks in [`auth_sessions.sql`](../ordelo_datamodels/admin_dashboard/auth_sessions.sql). A prior actor must lose access via old dashboard links or sessions after a move. When an invite-only rider later requests dashboard access that needs phone proof, offer the existing contact button at that point. Update the same-account contact path to record proof when the rider shares their own matching Telegram contact. Verify that this grants dashboard access without changing their rider identity.
5. **Reconcile ADR 0011 and the restaurant-admin rollout.** Amend [ADR 0011](../docs/adr/0011-telegram-operations-messaging-stays-in-ordeloagent.md) D39 for the new invite path. Keep D40's rider identity on `rider_master`. The [restaurant-admin P3 plan](restaurant-admin-roster-onboarding-plan.md#7-p3-cut-over-date-chosen-by-the-owner) already retains `t_invites` for audit. Update it to retain the rider issue/claim operations, code generation and service-role access as well. Scope the optional P1 pending-invite revocation to `bot_key = 'rest_admin'`. Review all restaurant readers and cleanup for bot-key filtering, retire only the admin invite functions and handlers at P3, and replace the old check for zero references to `t_invites` with a check that the admin flows have no invite dependency. Update the [Telegram guide and change log](../docs/telegram-layer.md) and the operator instructions alongside implementation.

## Handoff and rollback

Apply the schema before enabling the rider invite route. Keep the CLI unused until the route and ops alerts have passed verification. A code rollback can disable the invite route and CLI use while leaving additive schema and audit records in place. Review and revoke only outstanding rider invites affected by the rollback. Review already claimed links individually because disabling issuance does not reverse them. Coordinate any shared schema rollback, routing change or deployment with the owner.

Hand off the changed files, test results, whether the migration was applied to the intended database, the live Telegram and dispatch evidence, and any remaining checks. A local test supplies no deployment evidence.
