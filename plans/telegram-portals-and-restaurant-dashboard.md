# Telegram portal access and the restaurant operations dashboard

Implementation handoff · 18 November 2026 · plan only. OrdeloAgent and restaurant-frontend are both on `docs/glossary-updaet`. Source baselines are `7cd530c` and `35b5065` respectively. Links below resolve from this file. New symbols and routes are proposals.

## Product decisions

- Riders use the Byteloop rider bot for their private jobs and earnings portal. Restaurant admins use the restaurant bot for one scoped dashboard per restaurant. A verified phone currently in overwatch gets an additional sysadmin option on the restaurant bot, including people assigned to zero restaurants.
- Complete all five Actions in phases. Start Reports with operational measures of acceptance and pickup. Orders already provides financial summaries.
- Confirmed 19 November: show both delivery pickup measures in the first operational report — elapsed time from order creation to verified rider collection, and minutes early or late against each of two benchmarks: the original promise and the latest promise in force at collection.
- Closed dates and hidden items apply to both web and WhatsApp ordering. A hidden item stays hidden until an authorized manager for that restaurant explicitly restores it. Notification preferences are the signed-in admin’s own channel choices, equivalent to Telegram `/channels`. These choices can affect multiple restaurants for one person.
- Confirmed interaction: eligible overwatch members see both a private restaurant-bot slash menu entry for `/sysadmin` and a “System dashboard” button under `/manage`. Keep the existing per-restaurant choices and the rider bot’s `/my_jobs`. WhatsApp uses `/login` and `/sysadmin`.

## Phase 1 · Complete portal access

**Separate a verified identity from its permissions.** Today [t_admin_link and t_admin_profile](../ordelo_datamodels/restaurant_admin/admin_roster.sql) use the roster for onboarding and admin status. An overwatch-only user cannot even complete their first contact share. Broadening `AdminProfile.is_admin` would give restaurant handlers the wrong answer. Keep restaurant permissions derived from `restaurant_master.admins`, system permission from the current exact phone entry in `ordelo_config.overwatch_list`, and the Telegram binding from the verified contact. A Telegram username, chat ID, legacy invite or rider-bot link supplies none of these permissions.

1. Extend the existing private [contact flow](../channels/telegram/rest_admin/router.py) and its SQL link transaction to admit a number on either list. Preserve `contact.user_id == from_user.id`, uniqueness on Telegram user, relink handling, existing alert choices and inbox protection for the contact update. Retain one binding per phone. Check every consumer of `restaurant_admin`, including alert destination and order-card RPCs, before admitting rows with zero restaurants. Such a row grants zero restaurant destinations, pause rights, order actions or settings. Document first-link channel behavior when that person is later added to a restaurant.
2. Add a small portal-access interface, e.g. `portal_options(tuid)` returning current restaurant targets and `can_open_sysadmin`, plus `issue_system_link(tuid)`. Put the verified actor lookup, fresh allowlist decision and scoped mint in the database transaction for Telegram issuance. Pass only actor ID and a locally generated token hash to the service-only RPC. Return a typed allowed/denied/unavailable result; assemble the URL only on success using [get_dashboard_app_url_async](../config/params.py). Keep credential format, TTL and hashes compatible with existing [auth_sessions](../ordelo_datamodels/admin_dashboard/auth_sessions.sql). Factor the exact, normalized allowlist test so [WhatsApp issuance and payout authorization](../watomation/routers/sys_admin_auth_session.py) agree with Telegram. Preserve store-unavailable versus ineligible outcomes. No HTTP endpoint accepting a caller-asserted phone is required.
3. Change the early exits in [cmd_manage](../channels/telegram/rest_admin/manage.py) so zero restaurants plus system access renders the system action; zero capabilities yields linking/removal guidance. Keep restaurant links usable during an independent system-option lookup failure. Use a short typed callback to request the system link, promptly acknowledge the tap, then send the privately minted URL with previews off. Direct `/sysadmin` goes through the identical actor check. The callback carries no identity or token. Recheck authorization even for an old button. Update [command/help text](../channels/telegram/rest_admin/commands.py), `cmd_start`, `_link_contact`, `cmd_help`, `cmd_whoami` and router order. Register only on the restaurant dispatcher before its fallback. For an eligible private chat, install the full restaurant command list plus `/sysadmin` using `BotCommandScopeChat`, following [the rider scoped-menu implementation](../channels/telegram/rider/commands.py). Delete the override on loss of eligibility. Reconcile already-linked chats at rollout, refresh after linking, relinking and allowlist changes, and repair stale menus on private interactions. Use the same eligibility decision for help and the button. Exercise both entry points and test that installing the override preserves the existing commands and restaurant buttons. Publish the ordinary menus per bot via [setup notebook](../notebooks/telegram/tgram_setup_bot.py). Keep raw URL, credentials and Telegram exception text containing URLs out of logs.
4. Bring [rest-admin activation](../../restaurant-frontend/app/rest-admin/activate/%5Btoken%5D/route.ts) and [sys-admin activation](../../restaurant-frontend/app/sys-admin/activate/%5Btoken%5D/route.ts) onto the [rider GET/POST pattern](../../restaurant-frontend/app/rider/activate/%5Btoken%5D/route.ts). Share the HTTP mechanics: GET/HEAD do not consume, browser auto-POST uses the configured HTTPS origin, private/no-store headers and strict-origin referrer policy. Configure role-specific target, expiry guidance and cookie. Preserve existing WhatsApp URLs and active cookies across deployment. A JavaScript-capable preview can still submit the page. Keep per-role exchange atomic and one-use, including concurrent taps; check current role authority at exchange, at protected requests and inside mutations. Confirmed: when a verified phone moves to a different Telegram account, revoke all existing rest_admin and sys_admin sessions and unused admin links for that phone across restaurant scopes and issuing channels in the same transaction as the relink. An open browser must request a fresh link on its next protected request. Repeating the contact share from the already-linked account leaves valid sessions intact. On unlink, invalidate outstanding credentials for the old binding. Test removal between mint, activate and write.
5. [lib/sys-admin-session.ts](../../restaurant-frontend/lib/sys-admin-session.ts) currently checks cookie, role, UA and time limits; only the payout backend independently checks current overwatch. Extend this gate for direct frontend reads/writes too. For restaurant sessions, bind current phone + scoped restaurant on every privileged operation through [lib/rest-admin-session.ts](../../restaurant-frontend/lib/rest-admin-session.ts). Preserve server-overwritten context headers, role-specific cookies and logout. Await actual heartbeat execution. Differentiate denial from transient database unavailability. Update both expired pages with the appropriate Telegram command and existing WhatsApp recovery option.

**Acceptance matrix.** Rider-only → rider link only. Ordinary admin → each own restaurant. Overwatch-only → system link only after self-contact on restaurant bot. Dual-role → both. Unlinked, removed, forwarded contact, group chat, stale callback and wrong bot → no privileged credential. An alert pause or WhatsApp-only notification preference does not revoke portal access. Two eligible people cannot reuse each other’s asserted phone to mint. Exercise independent failures without leaking one user's links to another.

Build operational cohorts separately using order creation day in Europe/London. Include the restaurant, fulfilment type, period, measured sample and eligible count. A bounded date picker, delivery/takeaway filter, daily rows and period summary fit the existing [Orders filters](../../restaurant-frontend/app/rest-admin/orders/DateRangeChips.tsx). Show empty, partial coverage and unavailable states.

| Proposed first metric | Definition and source requirement |
|---|---|
| Manual acceptance time | Median minutes from summary creation to first human acceptance. Report manual accepted count, configured auto-accept, timeout fallback and declines separately. Capture the first transition transactionally for both fulfilment types. |
| Actual delivery pickup | Median minutes from creation to first verified rider pickup, plus separate median differences against the first promised pickup time and the latest promised pickup time at collection. Compute actual minus promise per order before aggregation; negative is early. Preserve the original on first promise and snapshot the effective promise at verified collection. With no adjustment the benchmarks coincide. Show coverage per metric when historical timestamps are missing. |
| Takeaway | Show manual acceptance and scheduled pickup lead time. Show actual collection only where a verified customer-collection event exists. Label ready, promised pickup and actual collection separately. |

Trace [order decisions](../ordelo_datamodels/restaurant_admin/restaurant_order_decision.sql), [delivery summary](../ordelo_datamodels/delivery/delivery_summary.sql), [takeaway summary](../ordelo_datamodels/takeaway/takeaway_summary.sql), [ready/adjust facts](../ordelo_datamodels/restaurant_admin/restaurant_ready_adjust_notices.sql), [dispatch lifecycle](../ordelo_datamodels/dispatch/delivery_dispatch.sql) and the `pickedup` write in [rider_agent.py](../ordelo/agents/rider_agent.py). Prefer durable, immutable source timestamps. Where absent, introduce nullable first-occurrence timestamps or a small order milestone table with a unique order/milestone key and a pickup-promise snapshot. Stamp at authoritative transitions, including non-Telegram paths; repeated updates do not rewrite history. Mark the coverage start; avoid inferred historical backfill. Add a service-only bounded aggregation RPC in `ordelo_datamodels/admin_dashboard/`; derive tenant from the validated session in a proposed `GET /api/rest-admin/reports/operations`. Accept date bounds and fulfilment type only. Return sample counts per metric, nullable medians and the reporting timezone; calculate period medians from observations. ## Phase 5 · Menu visibility across both ordering paths

Implement reversible hide/show for a specific restaurant and catalogue item. The [menu DDL](../ordelo_datamodels/core/menus.sql) contains restaurant-specific tables; [the storefront menu route](../../restaurant-frontend/app/api/menu/route.ts) fetches `MENU_API_URL` using the configured restaurant API name and maps availability to stock. Hiding must preserve stock data and historical order lines. First trace the producer of that external feed and catalogue identifiers for each restaurant. Establish a stable key that matches a submitted order item, including aliases, brand variants and duplicate display names. The web checkout model already includes `Item.sku`; inspect the WhatsApp checkout payload before selecting the common key.

Recommended storage is a small visibility override keyed by canonical restaurant and stable item key, with absence meaning visible. Add a scoped search/list with current visibility, a hide/show control and an idempotent write; never interpolate a browser-supplied table name. Apply the same decision to visible catalogue rows and the transactional order validation in both paths above. On submission of a stale cart, identify affected lines and allow correction before any new payment session. Preserve historical menus on existing orders. Test a hidden item across London midnight, a catalogue refresh and the next service opening on both channels. Verify that only explicit restoration clears the visibility override and that the existing stock status still applies. Also cover stale cart, same SKU at another tenant, cached feeds and a catalogued item accessible from a previously sent WhatsApp link. If a restaurant also exposes a native WhatsApp catalogue, trace its publisher and sync supported visibility there before declaring customer-facing parity. The `MENU_API_URL` owner and native catalogue coverage were not independently verified.
