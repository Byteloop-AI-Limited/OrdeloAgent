# Pickup Time Logic

Runtime flow for `pickup_time` in `delivery_summary` and `takeaway_summary`.

---

## Configured Restaurant Auto-Accept

`restaurant_master.auto_accept` defaults to `false`. When enabled, the shared
database policy resolves a positive whole-minute pickup duration from the
restaurant-specific key, falling back to the corresponding global key:

- Delivery: `{REST_REF}_DEFAULT_DELIVERY_PICKUP_TIME` then
  `DEFAULT_DELIVERY_PICKUP_TIME`
- Takeaway: `{REST_REF}_DEFAULT_COLLECTION_PICKUP_TIME` then
  `DEFAULT_COLLECTION_PICKUP_TIME`

The initializer inserts the pickup time and marks the order with
`restaurant_confirmation_status='auto_accept'` and
`rest_confirmation_method='configured_auto'`. Delivery starts `unassigned`;
takeaway starts `pickup_confirmed`. This skips the restaurant confirmation
webhooks and cron timeout flow. Invalid/missing global configuration fails the
auto-accept initialization instead of inventing a pickup time.

Configured auto-accept suppresses delivery's "No Rider Found" admin message.
It retains payment/print work, restaurant webhooks, overwatch,
customer/rider messages, delivery operational receipts, and the takeaway admin
receipt.

## A. Delivery Orders (`delivery_summary`)

### Trigger chain (DB → API handler)

- Source trigger is in `ordelo_datamodels/summary.sql`:
  - `trigger_restaurant_updates` on `delivery_summary` (`AFTER INSERT OR UPDATE OF restaurant_confirmation_status`)
  - trigger function `restaurant_updates_whook()` posts to `/delivery-hooks/restaurant-confirmation-request`
- In `watomation/routers/delivery_hooks.py`, `restaurant_confirmation_flow()` routes by `trigger_reason`.
- When `trigger_reason='restaurant_accept'`, it schedules `_handle_restaurant_accept()` (this is how pickup-time options are kicked off).

### 1) Restaurant accepts order → pickup options sent

- `watomation/routers/delivery_hooks.py` in `_handle_restaurant_accept()` sends pickup choices to admins.
- Choices are generated by `utils_common/waba_utils/wa_senders.py` in `send_restaurant_pickup_time()`.
- Default options are `+5`, `+15`, `+25` minutes from `delivery_summary.dtts`.
- Callback action used in buttons is `/PickupTime`.

### 2) Admin selects pickup time → DB update

- `watomation/on_callback_wa_handler.py` in `handle_pickup_time_selection()` handles `/PickupTime`.
- It updates `delivery_summary` with:
  - `pickup_time = selected value`
  - `status = 'unassigned'`
  - `restaurant_admin`, `restaurant_update_dtts`
- Update is gated by `restaurant_confirmation_status = 'restaurant_accept'` to avoid stale/duplicate writes.

### 3) Timeout path if no pickup time selected

- `ordelo_datamodels/jobs_n_functions/process_restaurant_confirmation.sql` runs every 5s.
- If `restaurant_confirmation_status` is `restaurant_unconfirmed` or `restaurant_accept` and `pickup_time IS NULL` past timeout, it sets `restaurant_confirmation_status` to `restaurant_timedout`.
- Timeout uses config:
  - `{rest_ref}_RESTAURANT_CONFIRMATION_TIMEOUT_TIME`
  - fallback `RESTAURANT_CONFIRMATION_TIMEOUT_TIME`
  - fallback default `5` minutes.

### 4) Auto-accept on timeout

- `watomation/routers/delivery_hooks.py` in `_handle_restaurant_timedout()` sets:
  - `pickup_time = dtts + N minutes` where N comes from `ordelo_config` (Europe/London timezone handling):
    1. `{rest_ref}_DELIVERY_PICKUP_DEFAULT_TIME` (restaurant-specific override)
    2. `DELIVERY_PICKUP_DEFAULT_TIME` (global default)
    3. hardcoded fallback `30` minutes
  - `restaurant_confirmation_status = 'auto_accept'`
  - `status = 'unassigned'`
- Admins are notified with the auto-assigned pickup time.

### 5) Admin adjustment after inflight (mid-delivery pickup-time change)

Once a delivery is inflight, a restaurant admin can adjust the pickup time from the order receipt message they received when the rider was assigned.

**Full chain:**

```
Admin taps "Adjust Pickup Time" button (+10 or +20 min)
  → /AdminAdjustPickupTime WA callback
  → admin_adjust_pickup_time() in on_callback_wa_handler.py
  → check_delivery_progress(order_number=order_number)
  → not AWAITING_PICKUP? → reply with GATE_REPLIES[progress], return (no DB write, no trigger)
  → UPDATE delivery_summary SET pickup_time=<new>, restaurant_confirmation_status='restaurant_pickuptime_adjusted'
  → trigger_restaurant_updates fires
  → restaurant_updates_whook() → POST /delivery-hooks/restaurant-confirmation-request
  → restaurant_confirmation_flow() dispatches to _handle_restaurant_pickuptime_adjusted()
  → check_delivery_progress(order_number=order_number) again (defence-in-depth)
  → not AWAITING_PICKUP? → log + return, agent never runs
  → run_rider_agent_w_custom_msg(state_update_dict={'pickup_time': <new>})
  → agent calls notify_pickup_time_adjusted tool
  → rider receives WhatsApp message with updated time
```

**Key point:** `run_rider_agent_w_custom_msg()` accepts an optional `state_update_dict` that patches values into the agent's LangGraph state **before** the LLM turn runs. This is how `notify_pickup_time_adjusted` reads the fresh `pickup_time` from state rather than re-querying the DB.

**Delivery-progress gate:** `check_delivery_progress()` (in `ordelo/delivery_progress.py`) resolves whether the order is still in `delivery_inflight` and, if so, whether its `delivery_dispatch.status` is `pickedup`/`completed`. See `CONTEXT.md`'s "Delivery progress" entry for the full state list. Because WhatsApp buttons never expire, `admin_adjust_pickup_time()` checks this **first** -- if the order is no longer inflight or the food is already picked up, no `delivery_summary` write happens at all, so `trigger_restaurant_updates` never fires and the rider is never notified. `_handle_restaurant_pickuptime_adjusted()` re-checks the same gate as defence-in-depth for any other path that could set `restaurant_pickuptime_adjusted` (e.g. manual SQL). Any read failure resolves to `UNKNOWN`, which both call sites also treat as a block -- a stale or unverifiable tap must not silently proceed.

This replaces an earlier guard, `is_food_already_picked_up()` (`ordelo/agents/agent_runner.py`), which read `is_restaurant_confirmation_code_verified` off the LangGraph checkpoint via the `get_latest_state` SQL function (see `docs/get_latest_state_guide.md`). That approach only covered the food-ready path, and went blind once a thread closed or was deleted -- `get_latest_state` resolves only active threads, so a *completed* delivery read back "not picked up" and let a stale tap through. The function is kept, unused, as a worked example of the RPC.

### 6) Downstream use

- `pickup_time` is included in rider dispatch payload/message flow (see `docs/dispatch_flow.md`).
- SQL payload wiring for restaurant webhook includes `pickup_time` in `ordelo_datamodels/summary.sql` (`restaurant_updates_whook()` JSON build).
- Once inflight, the admin receives an order receipt (`admin_order_reciept()` in `wa_senders.py`) with a "Ready - Notify Rider" button (`/AdminCollectionReady`). Tapping it invokes `admin_collection_ready()` in `on_callback_wa_handler.py`, which calls `run_rider_agent_w_custom_msg()` to trigger `notify_food_ready_for_pickup` on the rider agent — unless the delivery-progress gate above reports the order is no longer inflight or the food is already collected. The same gate protects the `/delivery-hooks/notify-food-ready-for-pickup/{recipient}` webhook, called from the sibling `restaurant-agents` repo's `admin_collection_ready`; that caller fires a bare `httpx` POST and never inspects the response, so an unresolvable gate read also returns a "skipped" `200` there (`action: "unknown"`) rather than a 5xx nobody would act on. See `docs/callback_handlers.md` for details.

## B. Takeaway Orders (`takeaway_summary`)

### Init paths

A `takeaway_summary` row is created by `init_takeaway_summary()`, which is called from two entry points:

- `POST /takeaway-hooks/init-takeaway-order` -- direct entrypoint for pay-at-restaurant takeaway orders (`watomation/routers/takeaway_hooks.py`).
- `POST /payment-hooks/pay-at-restaurant/{rest_ref}` -- called by the restaurant frontend checkout page; sets `food_order.payment_status = 'pay_at_rest'` then calls `init_takeaway_summary()` as a background task (`watomation/routers/payment_hooks.py`).

### Trigger chain (DB → API handler)

Two triggers exist on `takeaway_summary` in `ordelo_datamodels/takeaway_summary.sql`:

1. **`trigger_takeaway_restaurant_updates`** — fires on `INSERT OR UPDATE OF restaurant_confirmation_status`
   - trigger function `takeaway_restaurant_updates_whook()` posts to `/takeaway-hooks/restaurant-confirmation-request`
   - Routed by `trigger_reason` in `watomation/routers/takeaway_hooks.py` → `restaurant_confirmation_flow()`

2. **`trigger_takeaway_pickup_time_set`** — fires on `UPDATE OF pickup_time` when `OLD.pickup_time IS NULL AND NEW.pickup_time IS NOT NULL`
   - trigger function `takeaway_pickup_time_whook()` posts to `/takeaway-hooks/pickup-time-updated`
   - Handled by `watomation/routers/takeaway_hooks.py` → `pickup_time_updated_hook()`

### 1) Restaurant accepts order → pickup options sent

- `watomation/routers/takeaway_hooks.py` in `_handle_restaurant_accept()` sends pickup choices to admins.
- Same button generation via `send_restaurant_pickup_time()` with `order_type="takeaway"`.
- Default options are `+5`, `+15`, `+25` minutes from `takeaway_summary.dtts`.

### 2) Admin selects pickup time → DB update

- `watomation/on_callback_wa_handler.py` in `handle_pickup_time_selection()` handles `/PickupTime`.
- When `order_type == "takeaway"`, it updates `takeaway_summary` with:
  - `pickup_time = selected value`
  - `status = 'pickup_confirmed'`
  - `restaurant_admin`, `restaurant_update_dtts`
- Also sends customer pickup confirmation inline.

### 3) Timeout path

- Same `process_restaurant_confirmation.sql` function handles both delivery and takeaway timeouts.
- Takeaway section updates `takeaway_summary` where `pickup_time IS NULL` past timeout.

### 4) Auto-accept on timeout

- `watomation/routers/takeaway_hooks.py` in `_handle_restaurant_timedout()` sets:
  - `pickup_time = dtts + N minutes` where N comes from `ordelo_config` (Europe/London timezone handling):
    1. `{rest_ref}_PICKUP_DEFAULT_TIME` (restaurant-specific override)
    2. `PICKUP_DEFAULT_TIME` (global default)
    3. Hardcoded fallback: `30`
  - `restaurant_confirmation_status = 'auto_accept'`
  - `status = 'pickup_confirmed'`
- Admins and customer are notified with the configured pickup time.

### 5) Pickup time set → external restaurant notification

When `pickup_time` transitions from NULL to a value (via admin selection OR auto-accept timeout), the **`trigger_takeaway_pickup_time_set`** trigger fires automatically:

```
UPDATE takeaway_summary SET pickup_time = '...'
  → trigger_takeaway_pickup_time_set
  → takeaway_pickup_time_whook()
    → builds payload: { takeaway_summary, restaurant_master }
    → HTTP POST → /takeaway-hooks/pickup-time-updated
  → pickup_time_updated_hook() (responds 200 immediately)
    → BackgroundTask: _handle_pickup_time_set()
      → get_restaurant_webhook_url_async(rest_ref, 'order-pickup-time-updated')
      → HTTP POST → external restaurant service
```

- Trigger condition: `OLD.pickup_time IS NULL AND NEW.pickup_time IS NOT NULL` — fires exactly once per order.
- Payload: full `takeaway_summary` row + `restaurant_master` data (no `food_order`/`order_items`).
- URL resolution: restaurant-specific via `get_restaurant_webhook_url_async(rest_ref, 'order-pickup-time-updated')`.
- Debug logging: entries written to `debug_log` table at each step (controlled by `ENABLE_TRIGGER_DEBUG_LOG` config).
