## Flows

### Order creation and payment

Both channels create the order the same way; payment authorisation is applied once and then starts fulfilment.

- **Basket to order** — WhatsApp (restaurant-agents) or the web checkout allocates an order number with get_next_daily_seq() and calls create_food_order_with_items(): food_order and order_item in one transaction. The web path also writes web_session_meta and web_order_request (idempotency). (`get_next_daily_seq`, `create_food_order_with_items`, `food_order`, `order_item`, `web_session_meta`, `web_order_request`)
- **Payment link** — Python asks the payment service for a link. Web orders get a page token in order_access_grant for tracking. (`order_access_grant`)
- **Authorisation** — The payment callback calls record_payment_authorised(): a payment_event row per provider event and food_order.payment_status requires_payment -> requires_capture, at most once. (`record_payment_authorised`, `payment_event`)
- **Start fulfilment** — /payment-hooks/payment-complete calls init_delivery() or init_takeaway(); see the delivery and takeaway flows. (`init_delivery`, `init_takeaway`)
- **Safety net** — job_payment_init_reconciler() would alert overwatch about paid orders with no summary row. It is NOT scheduled on live (docs/to-do.md). (`job_payment_init_reconciler`)
- **Late or failed web payments** — Cancellations that must be retried are queued in web_payment_release and worked by the Python lifecycle sweep, which pg_cron job_web_lifecycle_sweep wakes every minute. (`web_payment_release`, `job_web_lifecycle_sweep`)

### Delivery order, from payment to doorstep

Statuses live in delivery_summary.status. Three 5-second cron jobs move an order from restaurant confirmation to an assigned rider.

- **1 Create** — init_delivery() inserts the summary: 'restaurant_unconfirmed', or 'unassigned' with a pickup time when resolve_initial_restaurant_acceptance() says the restaurant auto-accepts. (`init_delivery`, `delivery_summary`, `resolve_initial_restaurant_acceptance`)
- **2 Confirm** — trigger_restaurant_updates POSTs /delivery-hooks/restaurant-confirmation-request; admins answer by WhatsApp or Telegram. restaurant_order_decide() and restaurant_order_set_pickup() record the answer; process_restaurant_confirmation() (10 s) times out unanswered orders. (`trigger_restaurant_updates`, `restaurant_updates_whook`, `restaurant_order_decide`, `restaurant_order_set_pickup`, `process_restaurant_confirmation`)
- **3 Options** — process_delivery() (5 s) opens one delivery_detail row per vehicle type by delivery_option rank, and marks the order 'timedout' when every vehicle type timed out (trigger -> /delivery-hooks/delivery-timedout). (`process_delivery`, `delivery_detail`, `delivery_option`, `trigger_delivery_summary_timedout`)
- **4 Offers** — job_create_dispatch() (5 s) inserts delivery_dispatch offers for get_available_riders(), which requires an active, in-shift, unpaused rider. The statement trigger POSTs /delivery-hooks/delivery-dispatch; each rider's channel determines whether the offer goes to WhatsApp or Telegram. job_rider_offer_alerts restarts unanswered Telegram offers after a decline and escalates once per dispatch round. (`job_create_dispatch`, `get_available_riders`, `delivery_dispatch`, `trigger_delivery_dispatch_whook`, `is_paused`, `job_rider_offer_alerts`, `rider_offer_alert`)
- **5 Assign** — job_assign_dispatch() (5 s) gives the order to the first acceptance (assign_accepted_dispatch): dispatch, detail and summary 'assigned' and a delivery_inflight row, whose trigger starts the rider agent. notify_missed_dispatches() tells the other riders. (`job_assign_dispatch`, `assign_accepted_dispatch`, `delivery_inflight`, `trigger_delivery_inflight_whook`, `notify_missed_dispatches`)
- **6 Deliver** — The rider agent checks the pickup code; dispatch_cancel_before_pickup() re-offers the order; dispatch_complete_func() marks everything 'completed' and removes the inflight row. job_rider_pickup_alerts() nudges riders around pickup time. (`dispatch_cancel_before_pickup`, `dispatch_complete_func`, `job_rider_pickup_alerts`, `rider_pickup_alert`)

### Takeaway (collection) order

Statuses live in takeaway_summary.status: restaurant_unconfirmed -> pickup_confirmed -> completed, or declined.

- **1 Create** — /takeaway-hooks/init-takeaway-order calls init_takeaway(): 'restaurant_unconfirmed', or 'pickup_confirmed' with a pickup time on auto-accept. (`init_takeaway`, `takeaway_summary`, `resolve_initial_restaurant_acceptance`)
- **2 Confirm** — trigger_takeaway_restaurant_updates POSTs /takeaway-hooks/restaurant-confirmation-request; the same decision rules as delivery record the answer; process_restaurant_confirmation() times out unanswered orders. (`trigger_takeaway_restaurant_updates`, `takeaway_restaurant_updates_whook`, `restaurant_order_decide`, `restaurant_order_set_pickup`, `process_restaurant_confirmation`)
- **3 Notify** — The first pickup_time (on update or at insert) fires trigger_takeaway_pickup_time_set / _insert -> /takeaway-hooks/pickup-time-updated, so the customer is told when to collect. (`trigger_takeaway_pickup_time_set`, `trigger_takeaway_pickup_time_insert`, `takeaway_pickup_time_whook`)
- **4 Ready** — restaurant_order_ready() (WhatsApp or Telegram Ready) sets ready_at / ready_by and the customer is told. (`restaurant_order_ready`)

### Restaurant admin decisions and kitchen actions

One set of SQL rules for both channels. The Telegram wrappers authorise the tapping admin first.

- **Decide** — restaurant_order_decide() records accept / decline ('declined' is terminal); restaurant_order_set_pickup() sets the pickup time. t_order_decide() / t_order_set_pickup() check t_order_admin_phone() first. (`restaurant_order_decide`, `restaurant_order_set_pickup`, `t_order_decide`, `t_order_set_pickup`, `t_order_admin_phone`)
- **Time out** — process_restaurant_confirmation() (10 s) marks unanswered orders 'restaurant_timedout'; Python then sets a default pickup time. (`process_restaurant_confirmation`)
- **Ready, +10, +20** — Once a rider has the job, restaurant_order_ready() (first tap per dispatch wins) and restaurant_order_adjust_pickup() (relative to pickup_time_initial). Telegram wrappers: t_order_ready(), t_order_adjust_pickup(). (`restaurant_order_ready`, `restaurant_order_adjust_pickup`, `t_order_ready`, `t_order_adjust_pickup`)
- **Kitchen receipts** — New Telegram receipts use t_alert_destinations() to exclude paused admins. Existing receipt copies remain live: job_t_receipt_refresh() (5 s) finds stale copies with t_receipts_stale() / t_receipts_take() and Python edits them. (`t_alert_destinations`, `t_receipt_status`, `t_receipt_snapshot`, `t_receipt_sent`, `t_receipts_stale`, `t_receipts_take`, `job_t_receipt_refresh`)
- **Plain notices** — t_notice_targets() uses t_alert_destinations() for new Telegram notices, leaving out paused admins; WhatsApp notices are unchanged. (`t_notice_targets`, `t_alert_destinations`)
- **Daily availability** — enquire_admin_availability() asks each restaurant's admins every morning whether they are open. (`enquire_admin_availability`)

### Portal links and dashboard sessions

One verified identity per phone; restaurant and system rights are re-derived on every link and request (ADR 0017).

- **Link** — A Telegram account links by sharing its own contact. t_admin_link() admits a phone that is on a restaurant's admin list or in overwatch (is_overwatch()); t_admin_profile() answers ok, ops_only, not_linked or not_on_roster. (`t_admin_link`, `t_admin_profile`, `is_overwatch`, `admin_roster`)
- **Issue** — ordelo/dashboard_links.py asks portal_access() what the actor may open, then mints one link per portal with rest_admin_dashboard_mint(), sys_admin_dashboard_mint() or rider_dashboard_mint(). Each mint re-checks authority and stores only the token hash in auth_sessions. (`portal_access`, `admin_actor_phone`, `rest_admin_dashboard_mint`, `sys_admin_dashboard_mint`, `rider_dashboard_mint`, `auth_sessions`)
- **Open and use** — The link's page auto-POSTs; admin_dashboard_activate() / rider_dashboard_activate() consume it once. admin_dashboard_touch() validates every request and re-checks roster or overwatch membership through admin_session_authorised(). (`admin_dashboard_activate`, `admin_dashboard_touch`, `admin_session_authorised`, `rider_dashboard_activate`, `rider_dashboard_touch`)
- **Revoke** — Relinking a phone to another Telegram account, or admin_unlink_telegram(), revokes that phone's rest_admin and sys_admin sessions and unused links with auth_sessions_revoke_phone(). (`auth_sessions_revoke_phone`, `admin_unlink_telegram`)

### Restaurant dashboard settings, closures and reports

Every write is session-bound and audited; closed dates and hidden items are enforced at order creation for both channels.

- **Session actor** — Each dashboard RPC takes the session id and calls rest_admin_session_actor(), which re-derives the phone and restaurant and re-checks membership. (`rest_admin_session_actor`)
- **Audited write** — restaurant_setting_change() writes one setting and its restaurant_settings_audit row in one transaction; sys-admin lists changes with restaurant_settings_changes() and undoes one with restaurant_setting_revert(). (`restaurant_setting_change`, `restaurant_settings_audit`, `restaurant_settings_changes`, `restaurant_setting_revert`)
- **Acceptance policy** — rest_admin_acceptance_set() changes auto_accept and the default pickup minutes atomically; restaurant_default_pickup_minutes() resolves them exactly as order creation does. (`rest_admin_acceptance_get`, `rest_admin_acceptance_set`, `restaurant_acceptance_apply`, `restaurant_default_pickup_minutes`)
- **My alerts** — rest_admin_alerts_* change the signed-in admin's channels (admin_set_channels) and pause (pause_start / pause_end with the last-admin guard), the same rules as the bot's /channels, /off and /on. (`rest_admin_alerts_get`, `rest_admin_alerts_set_channels`, `rest_admin_alerts_pause`, `rest_admin_alerts_resume`)
- **Closed dates** — rest_admin_hours_* store one-date overrides in service_hours_json.dates (gated by hours_edits_enabled()); service_hours_open() is the shared reading rule. (`rest_admin_hours_close_date`, `rest_admin_hours_set_date`, `rest_admin_hours_clear_date`, `rest_admin_hours_set_weekly`, `service_hours_open`, `hours_edits_enabled`)
- **Hidden items** — rest_admin_menu_set_hidden() adds or removes menu_item_hidden rows keyed by menu_item_key(title); the storefront reads menu_hidden_keys(). (`rest_admin_menu_list`, `rest_admin_menu_set_hidden`, `menu_item_hidden`, `menu_hidden_keys`)
- **Order guard** — create_food_order_with_items() calls order_intake_block() first and refuses with P0C01 (closed date, via restaurant_closed_by_override()) or P0C02 (hidden item). (`create_food_order_with_items`, `order_intake_block`, `restaurant_closed_by_override`)
- **Reports** — order_milestone_capture() stamps the first restaurant decision into order_milestone; rest_admin_report_operations() reports acceptance and pickup against the first and latest promise. (`order_milestone`, `order_milestone_capture`, `rest_admin_report_operations`)

### Telegram layer

Admins link their Telegram account through an invite; every update is handled at most once; order cards follow the database.

- **Invite** — The operator inserts a t_invites row and copies invite_link from t_invites_shareable. /start <code> calls t_invite_preview(); 'Yes' calls t_claim_invite(); /whoami calls t_linked_restaurants(). (`t_invites`, `t_invites_shareable`, `t_invite_preview`, `t_claim_invite`, `t_linked_restaurants`)
- **Inbox** — Each Telegram update is claimed once with t_inbox_claim() and closed with t_inbox_finish(), so retries across workers are skipped. (`t_inbox`, `t_inbox_claim`, `t_inbox_finish`)
- **Order cards** — job_t_order_alerts() (5 s) seeds checkpoints for unconfirmed orders and POSTs due reminders and stale copies to the app. New cards use t_alert_destinations() to exclude paused admins; existing cards remain visible and tappable, and their stale copies are still refreshed. (`job_t_order_alerts`, `t_order_alerts`, `t_alert_destinations`, `t_order_card_snapshot`, `t_order_cards_stale`, `t_order_cards_take`, `t_order_card_sent`, `t_order_card_mark`, `t_sent_messages`)
- **Admin alert pause** — Restaurant bot /off and /on call t_admin_pause() and t_admin_resume(); pause_start() refuses a pause that would leave no unpaused admin for that restaurant. t_admin_pause_status() supplies the current state and duration choices. (`t_admin_pause`, `t_admin_resume`, `t_admin_pause_status`, `pause_start`, `pause_options`)
- **Housekeeping** — t_housekeeping() purges old inbox, ledger and alert rows. It is NOT scheduled on live (docs/to-do.md). (`t_housekeeping`)

### Rider location

Continuous tracking from the OwnTracks app, plus on-demand WhatsApp or Telegram rider location replies.

- **Queue** — OwnTracks messages land in the pgmq queue 'owntracks'. job_process_owntracks() (30 s) moves GPS fixes to rider_location and region events to rider_location_event. (`job_process_owntracks`, `rider_location`, `rider_location_event`)
- **Events** — trigger_rider_location_event_update POSTs every region event to /location-hooks/notify-rider-location-event. (`trigger_rider_location_event_update`, `rider_location_event_update`)
- **Missing fixes** — job_null_or_outdated_location() would alert about live jobs with no recent fix; its cron job is INACTIVE. (`job_null_or_outdated_location`)
- **On demand** — A customer or admin asks where the rider is: wa_location_request (pending) -> the assigned rider's WhatsApp or Telegram prompt -> a one-time location share -> wa_location_observation -> requests fulfilled. Telegram shares are stored as telegram_current; restaurant-agents currently receives the compatible whatsapp_current wire value. (`wa_location_request`, `wa_location_observation`)

### Customer notifications

utils_common/notify/customer_notifier.py writes events and delivers them through the outbox.

- **Subscribe** — Web orders get a 'web_page' subscription with no destination; WhatsApp customers get 'whatsapp_restaurant'. (`order_notification_subscription`)
- **Record** — One order_customer_event per order and deterministic event key. (`order_customer_event`)
- **Deliver** — One notification_outbox row per event and subscription, claimed before any I/O; web-page delivery is a no-op because the page reads events. (`notification_outbox`)

### Agent threads

thread is owned by restaurant-agents; LangGraph writes the checkpoint tables. OrdeloAgent reads state and closes idle threads.

- **Read state** — get_latest_state() / get_latest_state_by_thread() return a thread's latest checkpoint as JSON. (`get_latest_state`, `get_latest_state_by_thread`, `thread`)
- **Close idle OrdeloAgent threads** — job_close_thread() finds threads idle longer than THREAD_INACTIVE_TIME_INTERVAL and POSTs them to /delivery-hooks/close-threads. Python (delivery_hooks.py) calls it; pg_cron does not. (`job_close_thread`)
- **Terminate idle restaurant threads** — job_terminate_stale_active_threads_new() (every minute, job 'jobTerminateStaleActiveThreadsNew') POSTs per restaurant to restaurant-agents. (`job_terminate_stale_active_threads_new`, `job_terminate_stale_active_threads`)

### Rider shifts and timed pauses

The clock decides when a pause ends; the scheduled sweep handles bookkeeping and messages, not availability.

- **Daily shift** — enquire_shift_availability() asks active WhatsApp riders at 11:00 UTC. WhatsApp Yes/No and the rider bot /on use rider_set_shift(), which refuses a non-active rider's Yes and an off request during a job. Telegram riders do not get the daily question. (`enquire_shift_availability`, `rider_set_shift`, `rider_master`)
- **Start or end pause** — Rider bot /off and /on use pause_start() and pause_end(), which refuse the rider while a delivery_inflight row exists; an operator can still end a pause. Telegram also hides those commands in that rider's chat during the job. Restaurant bot /off and /on use t_admin_pause() and t_admin_resume(). Duration keys come from pause_options() and ordelo_config. is_paused() computes the current state from ends_at. (`delivery_inflight`, `pauses`, `pause_options`, `pause_start`, `pause_end`, `is_paused`, `t_admin_pause`, `t_admin_resume`, `ordelo_config`)
- **Sweep messages** — job_pause_sweep() closes expired pause rows and POSTs due ends-soon and back-on messages to /pause-hooks/sweep. A successful HTTP response marks the rows; actual message delivery is not confirmed by that response. Live pg_cron is active every five minutes (23 Oct); the file targets every minute, not applied. (`job_pause_sweep`, `pauses`)

### Dashboard and operations

Admin dashboard reads and platform helpers.

- **Dashboard** — Magic-link logins in auth_sessions; orders from v_admin_orders and its daily / monthly totals; get_rider_payout_report() for payouts. (`auth_sessions`, `v_admin_orders`, `v_admin_orders_daily`, `v_admin_orders_monthly`, `get_rider_payout_report`)
- **Daily rider question** — enquire_shift_availability() asks active WhatsApp riders whether they are working today; Telegram riders use /off and /on instead. (`enquire_shift_availability`, `rider_master`)
- **HTTP helpers** — ordelo_post() builds a URL from an ordelo_config key; fly_post() drives Fly.io machines with tokens from fly_config (security finding in docs/to-do.md). (`ordelo_post`, `ordelo_config`, `fly_post`, `fly_config`)
- **Switches** — job_awsrunner_switch() pauses or resumes AWS App Runner; both cron jobs are INACTIVE. (`job_awsrunner_switch`)
